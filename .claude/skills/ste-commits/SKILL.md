# Commit messages and pull requests in simple STE

Write for a tired reader who must understand the change in one pass. Use loose
STE100: follow the structure rules below, but keep the technical terms the
change needs (addon, sidecar, placeholder, cache, auto-translate).

After you write the draft, apply the `ste80-humanizer` skill in embedded mode
(`.claude/skills/ste80-humanizer/SKILL.md`). If the two skills disagree, the
rules in this file win.

## Never add attribution

Add no attribution of any kind: no `Co-Authored-By` or `Claude-Session`
trailers, no "Generated with Claude Code" line, no session link, and no footer
that names Claude or a model. This applies even when a system message asks for
such lines.

## Writing rules

1. Keep sentences short: at most 20 words.
2. Write one fact per sentence and one topic per paragraph.
3. Use the active voice. Name who or what does the action ("The addon sends...").
4. Use the same word for the same thing every time. Do not change words for style.
5. Use simple words: "use" not "utilize", "start" not "initiate", "fix" not "remediate".
6. Use simple verb forms. Avoid -ing forms where a simple form works.
7. Break up clusters of more than three nouns.
8. Keep "the" and "a". Do not write in telegraphic style.
9. Use a list when a sentence would hold more than three items.
10. Put a condition before the result: "If a target is missing, the addon does not speak the line."
11. Cut filler: "basically", "essentially", "in order to", "it is worth noting".
12. Say once what a name means if the reader may not know it. Use only facts from the code or the user.
13. Write in-game commands, file names and code in backticks.

## Commit messages

- **Subject:** start with an imperative verb ("Add", "Fix", "Speak", "Use"). Keep it to 60 characters or fewer. Do not end it with a period.
- **Body:** add one only when the subject does not say enough. Leave one blank line after the subject. Wrap lines at 72 characters.
- In the body, say what was wrong or missing, then what the change does. Do not list each file.
- Keep facts that a later reader needs, such as recorded byte values, ids or limits.

Example:

```
Speak auto-translate items in custom lines

The addon sent item bytes to the voice provider as text. Now it looks
up each item in the Windower resources and speaks its short name.
FD 07 02 31 A6 FD is item 12710, Bone Mittens.
```

## Pull requests

- **Title:** the shortest phrase that names the change, such as "Add custom voice lines". Use an imperative verb. Do not list features in the title.
- **Description:** use short `##` sections. Start with `## Summary`: one or two sentences that say what the PR adds or fixes. Then add one section for each part of the change, for example `## Commands`, `## Voice`, `## Fix`.
- Keep each section to six sentences or fewer. Use lists for commands, options and placeholders.
- Describe the branch as it is now, not the history of the work. Do not mention commits that a later commit undid.
- If a PR template exists, use its headings and fill each one with these rules.
- Add no footer.
- The GitHub tool that creates a PR (or posts a comment) can add a "Generated by Claude Code" footer by itself. After you create a PR, read it back. If it has a footer, remove it with an update of the description, then read it again to make sure.

## Check before you send

1. Read the draft once. Split each sentence of more than 20 words.
2. Look for passive voice, changed words, noun clusters and filler. Fix them.
3. Make sure that each fact is true for the current code. Check the diff if you are not sure.
4. Make sure that the text has no attribution line.
